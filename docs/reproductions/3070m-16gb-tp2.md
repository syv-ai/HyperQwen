# Reproduction: 2x RTX 3070M 16 GB (TP=2), no P2P, PCIe 3.0 x8, every setup

*October 2026. Docker Compose, the published image at `ce9615c` (vLLM 0.31.0). Two Dicasver RTX 3070M 16 GB
boards (GA104M, the laptop chip on a desktop PCIe card, sm86), TP=2, no P2P between them.*

[← back to the reproductions index](README.md)

Setups A to E from the [main README](../../README.md#which-setup-do-i-want), each as shipped, plus what A needed
to run at all. The four-card run of the same box is a separate report.

## .env

The common part, then the setup's lines from the README table:

```
GPU_COUNT=all
CUDA_VISIBLE_DEVICES=0,1
NCCL_P2P_DISABLE=1
EXTRA_ARGS="--tensor-parallel-size 2 --disable-custom-all-reduce"

# B:  SPEC=dflash2 PREFIX_CACHE=1
# C:  SPEC=dflash2 PREFIX_CACHE=1 DFLASH_TOKENS=15
# D:  SPEC=mtp CTX=long PREFIX_CACHE=1
# E:  SPEC=dflash2 PREFIX_CACHE=1 CTX=huge
# A:  nothing (--profile batch); see "Setup A" for the GPU_UTIL it needed
```

## Method

The README's field-test protocol per setup: boot, `bash bench/run_benchmarks.sh single` (or `batch --prefill
--long`) twice, keep the second run, then `bench/quality_battery.py <tag> --gsm-only`. Nothing else ran on the
cards. `nvidia-smi dmon` logged power, clocks and PCIe throughput through every run.

## Setup A (batch)

**As shipped it does not boot on these cards at TP=2.** Every start died in CUDA-graph capture with `CUDA error: out of
memory` (`torch/cuda/graphs.py`, FULL graphs, capture up to 64) at the launcher's `GPU_UTIL=0.94`, and
`restart: unless-stopped` restarted it five times before I stopped it.

- **CUDA-graph capture capped at 16 concurrent requests** (the A5000 TP4 report's workaround: the launcher's
  `--compilation-config` string with only `max_cudagraph_capture_size` changed from 64 to 16): boots, KV pool 431,443 tokens, then dies on the first
  64-concurrent cohort with an allocation failure inside `marlin_gemm` (`aten::empty` in the worker). It moves the
  OOM from capture to serving.
- **`GPU_UTIL=0.90`**, nothing else changed (capture back at 64): boots in 183 s with a 385,824-token pool
  (6.1 GiB per card), serves both passes and the GSM8K run without a restart. The rows below are this
  configuration, so they are not the untouched setup A.

| | result |
|---|---|
| 64 concurrent, 128 in / 512 out | **e2e 683.9 tok/s**, C / median TPOT 740, median TPOT 86.5 ms, mean TTFT 3.8 s |
| 64 concurrent, 256 in / 256 out | e2e 481.8 tok/s, C / median TPOT 556 |
| cohorts C1 / C2 / C4 / C8 (default temperature, no speculation) | 45.6 / 82.5 / 153.6 / 261.2 tok/s |
| prefill, one request: 1k / 4k / 16k / 64k / 100k | 1,147 / 1,170 / 1,125 / 923 / 810 tok/s |
| prefill 1k at 4 / 16 concurrent | 1,199 / 1,223 tok/s |
| 1x 100k prompt, 256 out | TTFT 122.3 s, TPOT 25.6 ms |
| 4x 60k prompts, 1024 out | 14.0 tok/s e2e, median ITL 35.4 ms |
| GSM8K (200) | 0.960 |

At 0.94 a 16 GB card keeps about 1 GB outside vLLM's budget, and 0.90 (about 1.6 GB) was enough.

## Quality

Every setup reads 0.960-0.965 on the 200-question GSM8K run.

## Power, link and what limits this box

- **Close to the power limit.** Loaded samples averaged 105-109 W against the 115 W limit on B-E, with the SM
  clock at 1.91-1.93 GHz (2.1 GHz max), 69-71 °C average, 78 °C peak. The vBIOS does not allow more than 115 W.
- **The all-reduce is NCCL's SHM transport over PCIe 3.0 x8** (no P2P): `dmon` showed peaks of 1.2-1.9 GB/s
  per direction on the single-user setups and 4.4 GB/s on batch.
