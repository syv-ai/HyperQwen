# A5000 24 GB (sm86) at 230 W: 1× batch, the first 4× TP4 (150k and 1M), and the TP2 all-reduce-count test

*September 2026. Two 4×A5000 nodes in a k8s cluster, image
`ghcr.io/syv-ai/hyperqwen@sha-d1c8a48` (vLLM 0.29.0 pin; 13 commits behind main
as of 2026-09-27) vs the 0.28-era image. The A5000 is the same GA102 silicon as
the 3090 reference — 24 GiB, 936 GB/s — power-capped at 230 W instead of 250 W.
This write-up consolidates the two field reports with the raw data:
[#228](https://github.com/syv-ai/HyperQwen/issues/228) (1× batch, 150k) and
[#229](https://github.com/syv-ai/HyperQwen/issues/229) (4× TP4, 1M, 0.28↔0.29
A/B), plus the 4× TP4 at the batch profile's own 150k context. No speculative
decoding: the pods run dense `--language-model-only`, so MTP/DFlash2 acceptance
is not part of these numbers.*

## 1×: batch, 150k — ~0.85–0.92× the 250 W 3090, i.e. the power cap, not an A5000 anomaly

64-concurrent (the `batch` reference shape), second run after a discarded
warmup:

| row | ours, 230 W | 3090, 250 W (repo batch) | ratio |
|---|---:|---:|---:|
| 128 in / 512 out | **958.6 tok/s** | ≈ 1,035 | **0.92** |
| 256 in / 256 out | 681.7 tok/s | — | — |

Real-prompt cohorts (`bench/prompts_real.jsonl`, 1,024-token answers, 1,130
input tokens per prompt; e2e = output-token throughput):

| cohort | default | greedy (T=0) | 3090, 250 W batch | ratio vs 3090 |
|---|---:|---:|---:|---:|
| C1 | 39.68 | 40.08 | 45.5 | 0.87 |
| C2 | 75.17 | 76.62 | 86.3 | 0.87 |
| C4 | 142.14 | 145.52 | 168.3 | 0.84 |
| C8 | 277.61 | 274.89 | 324.9 | 0.85 |

The ratio is stable at 0.84–0.92 across the ladder. The 3090 reference's own
power-cap data ([#62](https://github.com/syv-ai/HyperQwen/issues/62): 200 W →
−33 %, 250 W → baseline) says a 230 W card should read somewhere in that
window — it does, with nothing else to explain. **The A5000 behaves like a
230 W 3090.**

### Cold prefill ladder (150k ceiling)

Salted seed per size (a unique leading salt, so no two sizes share a prefix and
the enabled prefix cache can't turn a larger size into a sub-second hit of a
smaller one); 2 prompts each, 1 output token. In = 2×size + chat template.

| len | mean TTFT | effective prefill |
|---:|---:|---:|
| 1,024 | 628 ms | 3.25k tok/s |
| 4,096 | 2,424 ms | 3.34k tok/s |
| 16,384 | 10,283 ms | 3.19k tok/s |
| 65,536 | 54,947 ms | 2.39k tok/s |
| 102,400 | 101,664 ms | 2.02k tok/s |
| **149,000** | **176,926 ms** | **1.68k tok/s** |

The 149k point is the max that fits: `prompt + chat template + output ≤
150,000`, and vLLM counts the template on top — a 149.9k prompt 400s. Usable
input budget ≈ 149.8k.

### Quality

`bench/quality_battery.py` full battery, in-pod, against the running server
(PPL over ~33k held-out tokens, GSM8K 200 greedy, thinking off):

| battery | ours (230 W) | repo published (3090, 250 W) |
|---|---:|---:|
| PPL en (wikitext-2) | 10.89 | 10.76 |
| PPL da (fineweb-2) | 11.07 | — |
| PPL code (vLLM source) | 3.50 | — |
| **PPL all** | **8.44** | 8.09 |
| **GSM8K (200, greedy)** | **94.0 %** | 96.5 % |

A hair below the published 3090 numbers, same band — no garbage, no
quantization breakage.

## 4× TP4, 1M: 0.29 regresses, and no config lever closes it

This is the first TP4 1M this repo has: the `multi-gpu.md` TP4 row is a
community 4×RTX-5060-Ti field report, not reproducible here. **The A/B**
(#229): a canary pod (0.29) and the 1M prod pod (0.28) on two 4×A5000 nodes,
**identical command line except the image**, both nodes 230 W, same driver,
same weights, exclusive GPUs, zero contention. The same script ran on two
independent days (24/09 and 28/09); within-version run-to-run stability is
1–2 % (0.28 128k: 1501 vs 1490 tok/s), so the gaps below are not noise.

| point (16 out, cold prefill) | 0.28 24/09 | 0.28 28/09 | 0.29 24/09 | 0.29 28/09 | Δ 0.29 vs 0.28 |
|---|---:|---:|---:|---:|---:|
| short 64 tok (×3) | 0.84–0.90 s | 0.71–0.90 s | 0.75–1.00 s | 0.88–1.00 s | parity |
| 16k | 8.9 s / 1807 | 8.9 s / 1805 | 11.4 s / 1407 | 11.4 s / 1408 | **−22 %** (both days) |
| 32k | 18.2 s / 1763 | 18.2 s / 1761 | 23.2 s / 1379 | 23.2 s / 1378 | −22 % |
| 64k | 38.4 s / 1668 | 39.1 s / 1636 | 48.6 s / 1318 | 48.8 s / 1312 | −21 % |
| 128k | 85.3 s / 1501 | 85.9 s / 1490 | 106.0 s / 1208 | 106.6 s / 1200 | −19 % |
| 256k | 206.5 s / 1240 | 207.0 s / 1236 | 248.2 s / 1031 | 250.4 s / 1022 | −17 % |
| 512k | 564 s / 908 | 564 s / 907 | 654 s / 783 | 659 s / 777 | −14 % |
| **1M** (999.7k prompt + 8 out) | **27 min 41 s / 602** | **28 min 21 s / 602** | **30 min 55 s / 539** | **31 min 04 s / 536** | **−10.5 % / −10.2 %** |
| C8 decode (2k in / 512 out) | 356 (24/09) · **378–385 isolated** (28/09) | | 232 → **312–313** with the config below | | −35 % raw 24/09; −12…−19 % best config |

Two measurement notes, for whoever re-measures:

- **The 1M 400.** A naive 1M probe (≈999.9k prompt + 16 output tokens) 400s on
  *both* versions — `prompt + chat template + output > 1,000,000`; the server
  counts the template on top, exactly like the 150k ceiling above. Usable
  budget at 1M is ≈ 999.8k. (First 400 on a 1M endpoint = this, not a bug.)
- **C8 right after a 1M sweep reads low.** The 28/09 post-sweep C8 on the 0.28
  pod read 280 tok/s; isolated (3 reps, no pre-sweep, pod idle) it reads
  378–385. If you sweep then measure, re-measure C8 after a settle, or the
  baseline is understated by ~25 %.

**Levers tested, all negative or no-op** (0.29 TP4, 1M profile, #229):

1. `VLLM_KV_CACHE_LAYOUT=HND` (force the 0.28-era layout on 0.29; 0.29's
   default is LBNHC) → no effect (64k 49.0 s vs 48.8 s; 128k 106 s vs 106.6 s).
2. `--mamba-cache-mode` → already `none` by default in both versions
   (verified in both `config/cache.py`); nothing to switch.
3. GDN prefill backend → on sm86 the only option is Triton/FLA
   (FlashInfer/CuteDSL GDN is Hopper/Blackwell); no second backend exists on
   this card.
4. `VLLM_PREFILL_ATTN=int8` (the patch's int8-QK prefill attention) → no-op:
   its gate requires a **bf16** KV cache; this profile runs **fp8** KV.
5. `VLLM_TRITON_USE_TD=1` → no-op: that env only exists in the `fused_moe`
   kernels; this model is dense.
6. `--max-num-batched-tokens 2048 → 8192` (4× fewer all-reduces per prefill) →
   prefill unchanged, decode regressed (242 tok/s, TTFT 6.5 s); reverted.
7. `--disable-custom-all-reduce` → no-op on this topology: vLLM auto-disables
   the custom all-reduce on >2 PCIe-only GPUs; both versions boot on NCCL
   (both log the FlashInfer all-reduce `world_size=4` fallback).

**The one 0.29 win on TP4 (keep it):** `--compilation-config
'{"max_cudagraph_capture_size":16,"custom_ops":["+silu_and_mul"]}'` (instead
of the 0.28-era `64` / `["+rms_norm","+silu_and_mul"]`) → **C8 decode 232 →
312 tok/s (+34 %)**, closing ~75 % of the decode gap. Prefill is untouched by
it.

**Quality (0.29 1M pod, same battery):** PPL all **8.41** (en 10.85 / da 11.04
/ code 3.48), **GSM8K 95.5 %** — identical to the 1× pod to within noise. The
0.29 regression on this profile is a **speed** regression, not a quality one.

## 4× TP4, 150k: the 0.29-vs-0.28 question at the batch profile's own context

The 1×/150k result is GO for 0.29 and the 1M/TP4 result is NO-GO — so which
way does it land at **150k/TP4**, the context the repo's own batch profile
serves? Same A/B method as the 1M section: one 4×A5000 node, both pods on the
image's **`batch` launcher** (`EXTRA_ARGS="--tensor-parallel-size 4"`, so the
numbers compare with the repo's batch table directly), identical env otherwise
(the reference configs' set: Marlin int8/mlp, sampler off, PCIe NCCL P2P/IB
off, `GPU_UTIL=0.95`). The only non-default flag on *both* pods is
`max_cudagraph_capture_size: 16` — the launcher's own default of 64 **OOMs at
CUDA-graph capture on a 24 GB TP4** (`capture_end → out of memory`, pod crash),
the second 24 GB/A5000 OOM class this repo hits. Measured 28/09 on the 0.29
and 0.28 images (the 0.30.0 pin that later landed on `main` was not measured
here either).

**Cohort ladder, real prompts, 1024-token answers (8 prompts per point, unique
salted seed each, greedy). The 0.28 pod was cold-JITed (151 s, no AOT cache for
this shape), so it was run twice — first run, then again warm:**

| | 0.28 (cold) | 0.28 (warm) | 0.29 |
|---|---:|---:|---:|
| C1 | 72.0 tok/s | 83.6 | 80.3 |
| C4 | 197.0 | 248.5 | 242.5 |
| C8 | 329.5 | 403.1 | 400.3 |
| C16 | 324.9 | 420.3 | 390.5 |

**Result: at 150k/TP4 the two versions are tied.** The 0.28 cold→warm spread
is +11 % at C1, +26 % at C4, **+22 % at C8** and +30 % at C16 — *larger than*
the 0.28→0.29 gap at every point, and the 0.29 leg sits *between* the two 0.28
runs (e.g. C8: 0.28 cold 329.5 / 0.29 400.3 / 0.28 warm 403.1). The
cold-JIT-depressed first run is a boot artifact, not a version difference, so
the version delta is **not measurable at 150k/TP4 within this harness's
run-to-run noise** — unlike the 1M A/B, where the 0.28 pod was warm on both
days and the −10.5 % reproduced to ±1–2 %. What the 150k result does give is
the *bracketing* the 1M NO-GO needs: the 0.28→0.29 regression appears at the
1M profile (1M KV pool, 16 seqs, long-horizon GDN/SSM state), not at 150k —
i.e. it is **not a TP4-in-general one**. The 4-way all-reduce caps the ladder
around C16 on both versions anyway (C16 ≈ 1.05–1.3× of C8 for each), the same
ceiling `multi-gpu.md` describes for the 3090 and its reason to prefer spec
decode over raw TP for many users. (The 64-concurrent row is excluded: the
0.28 pod's first 64-conc run carried a 26 s first-request TTFT from the same
cold JIT, making its 422→522 tok/s spread a queue artifact, not a version one.)

**The 150k/TP4 24 GB ceiling is ~16–32k per single request, not 149k.** Both
versions crash the pod on a single 65k+ prefill: the `batch` launcher enables
prefix caching, which on 0.29 sets `mamba-cache-mode align`, and the GDN/SSM
recurrent state of *one* 65k prompt is proportional to its length — enough to
exhaust the 23.55 GB per-rank budget mid-request (the pod dies, it doesn't just
reject; the 64-seq KV pool is *not* the cause, it's ~9 % used at C8). So a
150k/TP4 24 GB deployment serves fine up to ~16–32k per request and its real
high-ctx single-request ceiling is far below `max-model-len`; going higher
needs prefix caching off (which turns off mamba align) or a lower
`GPU_UTIL`/`max-num-seqs`. The 1× profile doesn't show this (one rank's 24 GB
holds a 149k state; it's the 4-way split that bites).

## 0.30 follow-up: the 1M/TP4 regression is unchanged

`main` moved to vLLM 0.30.0 while the A/B above was on 0.29, so the open
question on #229 — *does 0.30 move it?* — needed the same run on the 0.30
image. Same method as the 1M A/B: a 0.30 canary
(`ghcr.io/syv-ai/hyperqwen:sha-8cf642e`, imageID `65f399a1…`, vLLM 0.30.0) and
the live 1M prod 0.28 pod, **identical command line and env (only the image
differs)**, both 4×A5000 at 230 W, same day (29/09), prod gated on idle. A
second canary on a free node covered the 1×/150k batch profile.

**Prefill (16 out, cold, salted), 29/09:**

| point | 0.28 | 0.29 (24/09) | 0.30 | Δ 0.30 vs 0.28 |
|---|---:|---:|---:|---:|
| 16k | 1,807 tok/s | 1,407 | **1,410** | −21.9 % |
| 32k | 1,762 | 1,379 | **1,381** | −21.6 % |
| 64k | 1,666 | 1,318 | **1,317** | −21.0 % |
| 128k | 1,500 | 1,208 | **1,209** | −19.4 % |
| 256k | 1,235 | 1,031 | **1,031** | −16.5 % |
| 512k | 907 | 783 | **783** | −13.7 % |

**1M (template-safe, 999.7k prompt + 8 out):** 0.28 **27:42 / 601 tok/s** vs
0.30 **30:55 / 539 tok/s** → **−10.2 %** (the 24/09 0.29 figure, 30:55 / 539,
reproduces to the minute).

**C8 (2k in / 512 out, isolated, 3 reps, warmup, no pre-sweep):** 0.28
**377–384 tok/s** (TTFT 1.3–1.5 s) vs 0.30 **311–340 tok/s** (TTFT 1.7–2.8 s) —
0.30 matches the 0.29 figure (312–313) almost exactly, i.e. it inherits the
0.29 decode, not a fix.

**1×/150k batch (second canary, free node):** 64-conc 128/512 **987 tok/s**
(0.29: 958.6), 256/256 700 (682); cohorts C1–C8 **39.8 / 75.3 / 144.8 / 285.6**
(0.29: 39.7 / 75.2 / 142.1 / 277.6); prefill 1k/4k/16k/65k
**0.61 / 2.35 / 9.9 / 53.3 s**; quality PPL all **8.55** (en 10.89 / da 11.07 /
code 3.70), **GSM8K 93.5 %** (0.29: 8.44 / 94.0 %). 0.30 stays GO on the 1×
profile.

**Result: 0.30 did not move the 1M/TP4 regression.** The 0.30 prefill and C8
are 0.29 to within run-to-run noise (16k 1410 vs 1407, 1M 30:55 vs 30:55, C8
311–340 vs 312–313), and both sit below the reproducible 0.28 baseline — so
the 0.28→0.29 regression is carried forward into 0.30, not a one-version blip.
The 1×/150k profile remains GO on 0.30. Two things are left open for whoever
picks this up: (1) the 0.30 image is the one the 1M prod would get, so if the
regression is ever fixed it is upstream of this image (or a config/launcher
change, which the #229 levers already ruled out). The 0.30 follow-up also
ran the #229 thread's suggested **TP=2** split (next section) to separate
"the gap scales with the all-reduce count" from "a 1M-specific prefill
regression".

## 2× TP2: the all-reduce-count test — TP2 is worse, and 1M doesn't even fit

The #229 thread's cheapest next measurement: run the same 1M sweep at TP=2
(2xA5000, a 2-GPU canary, same command line and env as the 4-way except
`--tensor-parallel-size 2`), to see whether the 0.28→0.29 gap scales with the
all-reduce count. Two things came out of it, one of which answers the question
and one of which closes the door on TP2 as an easy fix.

**First, 1M does not fit in TP2 on a 24 GB card.** At TP2 the model's 2 KV
heads are split 1 per GPU, so each rank holds 2× the per-rank KV of the 4-way
split. vLLM refuses to boot:
`ValueError: To serve ... max seq len (1000000), 15.33 GiB KV cache is needed,
which is larger than the available 13.22 GiB; estimated max model length is
860800.` So a TP2/24 GB box tops out at **~860k**, not 1M — you cannot "just go
TP2" to serve 1M; the 2-GPU and 4-GPU boxes fit different maximums. The TP2
canaries below run at `--max-model-len 800000` and the sweep goes to 512k
(both 0.28 and 0.30, both 2xA5000 at 230 W, measured 29/09).

| point (1 out, cold) | 0.28 TP4 | 0.28 TP2 | 0.30 TP2 | 0.28→0.30 @TP2 | TP2-vs-TP4 (0.28) |
|---|---:|---:|---:|---:|---:|
| 16k  | 1,807 tok/s | 1,407 | 1,473 | +4.7 % | **−22 %** |
| 32k  | 1,762 | 1,353 | 1,420 | +5.0 % | **−23 %** |
| 64k  | 1,666 | 1,256 | 1,311 | +4.4 % | **−25 %** |
| 128k | 1,500 | 1,094 | 1,126 | +2.9 % | **−27 %** |
| 256k | 1,235 | 861 | 869 | +0.9 % | **−30 %** |
| 512k | 907 | 600 | 595 | −0.8 % | **−34 %** |
| **C8** (2k/512, isolated) | 377–384 tok/s | **179** | **184** | +2.3 % | **−53 %** |

Two readings, which are the answer to the #229 question:

1. **TP2 is worse than TP4, and it gets worse with size.** The TP2-vs-TP4 gap
   widens from −22 % at 16k to −34 % at 512k on prefill, and −53 % at C8
   decode. That is the 2×-per-rank KV + 2×-per-rank GDN/SSM state + a 2-way
   (not 4-way) all-reduce all taxing the 24 GB rank — so **the "cheaper" 2-GPU
   shape is not a cheaper *service* on this card**: it is slower, and it
   cannot even hold 1M. If the goal is to drop the all-reduce count to dodge
   the regression, TP2 makes it worse, not better.

2. **The 0.28→0.29 gap is the same at TP2 as at TP4 (≈ 0).** 0.30-vs-0.28 at
   TP2 is +4.7 % / +5.0 % / +4.4 % / +2.9 % / +0.9 % / −0.8 % across 16k→512k
   and +2.3 % at C8 — i.e. 0.30 is *0.28 to within run-to-run noise* at TP2,
   just as at TP4 (the 0.30 follow-up above). So the 0.28→0.29 change did not
   *introduce* a TP2-specific regression either; the TP2-vs-TP4 gap is a
   hardware/TP-shape effect, present identically on both versions. The
   0.28→0.29 story is the same at 2-way as at 4-way: a 1M-profile effect,
   not an all-reduce-count effect.

## Takeaways

- **A5000 230 W ≈ 0.85–0.92× the 250 W 3090** across the whole 1× ladder —
  the power-cap ratio, nothing A5000-specific.
- **0.29 is GO on 1×/150k** (parity-or-better vs the 0.28-era build, better
  solo TTFT) **and a NO-GO on 1M/TP4**: −22 % → −10.5 % prefill, −35 % raw C8
  decode, reproduced over two days, not closed by any config lever — the
  suspected cause is the 0.29 GDN/chunked-prefill rewrite under tensor-
  parallel sharding on PCIe. Keep 0.28 for 1M. **The 0.30 follow-up (above)
  shows the regression is carried into 0.30 unchanged** — the pin on `main` is
  0.30.0 and it is not the fix.
- **The TP=2 all-reduce-count test (above) rules out the "drop the all-reduce
  count" theory**: 0.30 is 0.28 to within noise at TP2 just as at TP4, so the
  regression is a 1M-profile effect, not an all-reduce-count effect. And TP2
  is not a cheap fix — it is *slower* than TP4 (−22 to −34 % prefill, −53 % C8
  decode, and it gets worse with size) and cannot even hold 1M on a 24 GB card
  (~860k max).
- **150k/TP4 is the in-between case, and it is a *tie***: 0.29 and 0.28 land
  within run-to-run noise of each other across the cohort ladder (the 0.28
  cold→warm spread, +11…+30 %, is larger than the 0.28→0.29 gap at every
  point, and 0.29 sits between the two 0.28 runs) — unlike the 1M A/B, where
  the warm 0.28 pod reproduced to ±1–2 %. So the 0.28→0.29 regression is
  **specific to the 1M profile** (1M KV pool, 16 seqs, long-horizon GDN/SSM
  state), not to TP4 in general. A 150k/TP4 24 GB box also only serves
  ~16–32k per single request (mamba-align OOMs at 65k+), and the 4-way
  all-reduce caps the concurrency ladder around C16 on both versions.
- **The 1M usable budget is ≈ 999.8k tokens** (the template is counted), same
  rule as the 150k ceiling.
